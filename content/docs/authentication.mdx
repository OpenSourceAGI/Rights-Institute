---
title: Authentication
description: How sign-in, Google OAuth, and Google One Tap are wired up with better-auth.
---

Authentication is handled by [better-auth](https://www.better-auth.com),
backed by Drizzle ORM against Cloudflare D1 / Turso. There are three ways to
sign in:

1. **Magic link** — a one-time sign-in link emailed via [Resend](https://resend.com).
2. **Google OAuth** — the standard "Sign in with Google" redirect flow.
3. **Google One Tap** — the Google-branded prompt that appears automatically
   for signed-out visitors, without a click.

## Server setup

`packages/auth/src/auth.ts` configures `betterAuth()` with the Drizzle adapter, the Google
social provider, and three plugins:

```ts
plugins: [
  oneTap(),       // exposes POST /api/auth/one-tap/callback
  openAPI(),
  magicLink({ /* ... */ }),
]
```

The `oneTap()` plugin adds a dedicated endpoint that verifies the Google ID
token server-side (via Google's JWKS) and creates a session — it is separate
from, and not interchangeable with, the regular `signIn.social` OAuth
endpoint.

## Client setup

`packages/auth/src/auth-client.ts` registers the matching `oneTapClient` plugin, which
knows how to talk to that endpoint. The one thing it needs up front is the
Google client ID — and getting that into the browser correctly is the part
worth understanding.

### Why the client ID isn't a `NEXT_PUBLIC_*` var

The obvious move would be `NEXT_PUBLIC_GOOGLE_CLIENT_ID`, inlined into the
client bundle at **build time** by Vite's `define` (the same mechanism
[vinext](https://www.npmjs.com/package/vinext) uses to replicate Next.js's
`NEXT_PUBLIC_*` convention). That works fine if the build step itself has
the variable — but this app deploys to Cloudflare Workers, where env vars
are just as commonly set as **runtime** vars/secrets (Cloudflare dashboard,
or `wrangler secret put`), which the Worker only sees per-request, long
after the bundle was built. A client ID set that way is invisible to a
build-time `define` — the deployed bundle would have `undefined` baked in
permanently until the next rebuild.

Since `GOOGLE_CLIENT_ID` is already required for the server OAuth flow
above, and a Google OAuth client ID isn't a secret (it's exposed in every
OAuth redirect and by the GSI script itself), the simplest fix is to read it
once per request on the server — where the Worker's runtime env **is**
available — and hand it to the browser explicitly, instead of relying on
build-time inlining at all.

### How it's wired

`app/layout.tsx` is a Server Component, so it can read the Worker's runtime
env per request via `lib/env.ts`'s `getEnv()` (which checks
`cloudflare:workers`'s `env` first, then falls back to `process.env` for
local dev). It serializes the value into an inert JSON `<script>` tag in
`<head>`:

```tsx
const googleClientId = getEnv('GOOGLE_CLIENT_ID') ?? '';
// ...
<script
  id="google-client-id"
  type="application/json"
  dangerouslySetInnerHTML={{ __html: JSON.stringify(googleClientId) }}
/>
```

`packages/auth/src/auth-client.ts` reads it back out of the DOM at module-eval time in the
browser (this runs before any client component mounts, since the script tag
is server-rendered into the initial HTML and better-auth's `oneTapClient`
plugin needs the client ID synchronously at `createAuthClient()` time — it
can't be passed in later per-call):

```ts
function getGoogleClientId(): string {
  if (typeof document === 'undefined') return '';
  const el = document.getElementById('google-client-id');
  if (!el?.textContent) return '';
  try {
    return JSON.parse(el.textContent) as string;
  } catch {
    return '';
  }
}

export const googleClientId = getGoogleClientId();

export const authClient = createAuthClient({
  plugins: [
    magicLinkClient(),
    oneTapClient({
      clientId: googleClientId,
      autoSelect: false,
      cancelOnTapOutside: true,
      context: 'signin',
    }),
  ],
});
```

`oneTapClient` then handles loading the Google Identity Services script,
calling `google.accounts.id.initialize`/`prompt`, exponential-backoff
retries, and POSTing the resulting ID token to `/api/auth/one-tap/callback`
— none of that needs to be hand-rolled.

`packages/auth/src/GoogleOneTap.tsx` is a tiny client component mounted in the
root layout that triggers the prompt once per page load, but only after the
current session has resolved, only if the visitor isn't already signed in,
and only if a client ID actually made it to the browser:

```tsx
useEffect(() => {
  if (isPending) return;         // wait until session is known
  if (session) return;           // already signed in
  if (!googleClientId) return;   // GOOGLE_CLIENT_ID not set anywhere the server could read it
  authClient.oneTap({ callbackURL: '/dashboard' });
}, [isPending, session]);
```

If One Tap never appears and there's a `GOOGLE_CLIENT_ID is not set`
warning in the browser console, the server genuinely couldn't read the
variable at request time — double check it's set (as `.env` locally, or as
a Cloudflare Worker var/secret in production) and that the deployment
actually restarted/redeployed after setting it.

## Regular "Sign in with Google" button

The `/login` page also offers a plain button that calls
`authClient.signIn.social({ provider: 'google', callbackURL: '/dashboard' })`
— a normal OAuth redirect, unrelated to One Tap. Both flows land the user in
the same `sessions` table.

## Required setup

Google One Tap validates the page **origin**, separate from OAuth redirect
URIs — see [Environment Variables](/docs/environment-variables) for the
exact Google Cloud Console settings you need (Authorized JavaScript origins
in addition to the OAuth callback URLs).

## When configuration is missing

Auth is built lazily, from the runtime env, on the first request that needs
it — not at module import — and each piece degrades on its own:

| Missing | Effect |
|---|---|
| `BETTER_AUTH_SECRET` or `TURSO_DATABASE_URL` | Auth can't start at all: session reads answer `200 null` (signed out) and every other `/api/auth/*` endpoint answers `503 {"error":"auth_unavailable","missing":[…]}` |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Google sign-in and One Tap are skipped; magic-link sign-in still works |
| `AUTH_RESEND_KEY` | Magic-link emails aren't sent (the link is logged instead) |

The signed-out fallback is deliberate. `GET /api/auth/get-session` runs on
every page load, so answering it with a 500 breaks the session hook and
takes the whole page down with it; answering "signed out" keeps the site
usable while the real reason is logged server-side (`wrangler tail`) as
`[auth] … auth is not configured, missing: …`.

To check what the *running* deployment can see without reading logs:

```bash
curl -s https://rights.institute/api/health
# {"status":"degraded","config":{"auth":false,…},"missing":["BETTER_AUTH_SECRET"]}
```

It reports presence only, never values.
